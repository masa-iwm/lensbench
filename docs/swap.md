# カタログレンズの差し替え探索

- `swap`: `--spec` の JSON の `slots`（差し替える玉のブロックの `block` id と、候補 `parts` の並びか `filter`
  （`vendor`・`efl`・`diameter` の範囲）、`flip` で向きも両方）の候補で差し替えた組をすべて並列に回し、組ごとに `vars` を
  最適化して、評価関数の小さい順に `--top` 個を出す。`vars` は系のパラメータの書き方に加えて、id のある空気のブロックを
  `id.t` で指せる（その空気が入る面の厚さ）。範囲は `"d1.t=0.5:40"`（片側は空でよい）か、オブジェクトの形
  `{"name": "d1.t", "min": 0.5, "max": 40}`（`min`・`max` は省ける。`state_vars` も同じ）。`efl` で系の焦点距離の目標も足せる（像だけの値は `image_merit`）。
  ほかに `merit`・`reference`・`rings`・`iters`・`state`・`max_count`（組の数の上限、既定 100000）。
- 同じ形の候補はまとめて解く: 置いた玉の面（面の説明を除くすべての欄。膜も）が同じ選び方（型番違いの同じ玉など）の組は 1 回だけ
  最適化し、結果をほかの組にも使う（結果は 1 組ずつ解いたときと同じで、結果の行は組ごとに出る）。粗いふるいの一段目はまとめない。
- `terms` で評価関数に項を足せる（`optimize --term` と同じ JSON の配列。焦点距離の下限 `{"type": "paraxial", "q": "efl", "min": 351}` など）。
  `starts` は出発点の並び（`[{"d12.t": 20}, {"d12.t": 150}]` のように変数の名前 → 初期値。書かない変数はプロジェクトの値）で、組ごとに
  すべての出発点から最適化して評価関数の最も小さい解を採る（結果の `start` にその番号。間隔の局所解が複数ある系向け）。
  `image_merit` は既定の像の項だけの値（`efl`・`terms` の項を含まない）。
- `states` で状態をまたいで探索する（ズーム位置など）: 組ごとに `states` の全状態の系を同時に最適化し（評価関数は全状態の像の項）、
  `state_vars` の変数（群の移動 `G2.shift` など）は状態ごとに別の値で、`vars` は全状態で共通の値で解く。`terms` の `config` は `states` の番号
  （1 始まり。状態ごとの倍率の目標などに）。結果の `vars` の状態ごとの変数に `state`、`states` に状態ごとの像の評価関数と焦点距離。
  `state` とは同時に使えない。
- `clear_aperture: true` で有効径の条件を足す: 差し替える玉の各面で、各視野の瞳の縁（上下左右）の実光線が面の半径（カタログの玉の
  半直径）の内側にあることを片側の条件の項にする（玉の外を通る組を、けった光線で良く見せずに落とす）。
- `jac` はヤコビアンの求め方: 既定の `"forward"` はすべて前進差分（差分の追跡が中心差分の半分）、`"fd"` はすべて中心差分、`"auto"` は解析的に求められる列が 16 個以上なら解析的に、少なければ中心差分（`optimize --jac`）。
  差し替え探索の変数（間隔・群の移動など少数）では差分の方が解析的より速い（1 組あたり 1 スレッドで前進差分 約 3.5 ms・中心差分 約 5 ms・
  解析的 約 12 ms、実カタログの 2 所。7 万組で中心差分と解析的の上位 1000 組は同じ組で評価関数の差は相対 2e-8 以下）。
  解析的な列は変数の数によらない手間が大きく、変数が中心差分で 16 個・前進差分で 25 個ほどを超えると解析的の方が速い（11 面の系。
  解析的の時間は変数 16 個未満で auto が中心差分に切り替える前の値）。前進差分は中心差分よりさらに約 1.4 倍速く、実カタログの 2 所・3,000 組で
  上位 300 組の顔ぶれ・順位は中心差分と同じ（評価関数の差は相対 3e-7 以下）。
- `prescreen: {"rings": 2, "keep": 1000}` で粗いふるいを先にかける（既定はなし）: 全組を `rings` 環の瞳の光線で最適化して、
  評価関数の小さい `keep` 組だけを本来の設定で最適化し直す。組が多いときの時間を減らす（実カタログの 2 所・5.6 万組で 4 スレッド
  で全組 52 秒が 38 秒、上位 1000 組は全組で回した上位と同じ組・同じ値）。残った組の結果はふるいなしのその組の結果と
  同じ。粗い評価で順位が大きく入れ替わる系では、本来の上位を落とすことがあるので `keep` を大きめにする。`serve` の結果の `screened` は残った組の数。
- `beam: {"width": 20, "passes": 2}` で全組の総当たりの代わりに所ごとのビーム探索をする（既定はなし、`prescreen` とは同時に使えない）:
  最初はプロジェクトの玉のまま、所を 1 つずつ候補の全部に替えて最適化し、評価関数の小さい `width` 通りを残して次の所へ進む。
  所を一巡するのを、残す選び方が変わらなくなるか `passes` 巡まで繰り返す。評価する組はおよそ `width` × 候補の数の和 × 巡回の数で、
  所が 3 つ以上で候補が多いときも回せる（`max_count` はこの見込みに当てる）。結果はすべての所を選んだ組だけで、各組の結果は総当たりの
  その組と同じ。所どうしの組み合わせの効きが強い系では総当たりの最良を見落とすことがあるので、`width` を大きめにする。
  `--out` には結果をまとめて書く（続きからは回せない。`serve` の結果の `screened` は評価した組の数）。
- `paraxial: {"efl_tol": 2}` で近軸の前ふるいをかける（既定はなし、`efl` の目標が要る）: 変数（範囲つきの厚さだけ、12 個まで）の
  範囲の角すべてで系の焦点距離を求め、`efl` ± `efl_tol`（省けば目標の 1 %）に届かない組を光線を追わずに落とす（結果は
  誤り「paraxial: … misses the target …」）。屈折力は厚さのそれぞれについて 1 次なので範囲の中の最大・最小は角にあり、
  落とした組は範囲のどの値でも目標に届かない。残った組の結果は前ふるいなしと同じ。状態があれば状態ごとに確かめる。
  ピックアップ・ソルブ・マクロのある状態や屈折率分布の媒質の厚さを動かす状態は 1 次とは限らないので確かめない（落とさない）。屈折力の求まらない角がある状態も確かめない。
- `filter` の候補の要約（焦点距離・径・中心厚）は、所をまたいで 1 品につき 1 回だけ、並列に作る（`--threads` に従い、候補はスレッド数に
  よらない。実カタログ 1.6 万品・2 所で準備が 1 スレッド 1.0 秒 → 0.55 秒、4 スレッド 0.20 秒）。
- 組の番号 `i` は所ごとの候補の番号の混合基数（最後の所が最も速く回る）。結果は組の番号だけで決まり、スレッド数によらない。
  `--out r.jsonl` で組ごとに一括実行の JSONL へ逐次書き出し、同じ探索（設定・プロジェクト・候補が同じ）の
  ファイルがあれば続きから回す（`--no-resume` で書き直す）。粗いふるいがあれば、一段目の評価関数も組ごとに `r.pre.jsonl`
  （`--out` の拡張子を `.pre.jsonl` にしたもの）へ書き、続きから回すときは書いた値を使う（`keep` を変えても一段目は回し直さない。残した組が変わるので `r.jsonl` は続きから回せず、誤りの文のとおり `r.jsonl` だけ消して回すと二段目だけ回し直す）。一段目の評価関数が有限でない組（評価できなかった組）は二段目に回さない。
  進み具合は「ふるい n/N」「組 m/keep」の 2 段で出る（GUI・`serve` から回す探索も、ふるいの間から進み具合が出て、ふるいの途中でも止められる）。
- 組ごとの展開では、カタログの玉（.zmx）を所の候補ごとに 1 回だけ読んで使い回し、プロジェクトは JSON を通さずに玉のブロックだけ
  差し替える（結果は変わらない。2 所・6,400 組・反復 0 で 1 スレッド 2.39 秒 → 2.02 秒）。
- 例: `examples/projects/P18_swap_two.json`。Rust は `lensbench_design::swap::SwapSearch`、Python は
  `lensbench.swap_search(project, spec, lens_catalogs=[…], out=…)`。
