# 版の付け方

lensbench の版の番号の決まり（開発者向け）。変更の記録は [CHANGELOG](https://github.com/masa-iwm/lensbench/blob/main/CHANGELOG.md)、
互換が切れる変更の移し方は [壊れる変更](changes.md)。

## 番号の意味（1.0 まで）

版は `0.X.Y`。

- **X を上げる**: 結果の値が変わるもの、ファイルの形式・CLI の引数・Python API・serve の書式が変わるもの（互換が切れる）。
- **Y を上げる**: 不具合の直し、互換を保った追加、速さの直し。
- 1.0 は、ファイルの形式と Python API を固めるときに。

## main の版

- main は「次の版の開発中」を名乗る（例: `0.5.0-dev`）。main から作った exe・wheel は `0.5.0-dev` と出るので、リリースの版と混ざらない。
- リリースは `v0.X.Y` のタグだけ。タグの前に版を `0.X.Y` にし、タグを打ったらすぐ main を次の開発中の版（`0.(X+1).0-dev`）に上げる。
- 途中で渡す版が要るときは `v0.5.0-rc.1` のようにリリース候補のタグを打つ。版は `0.5.0-dev` のまま上げない（リリースのビルドは
  `0.5.0-dev` に対する `v0.5.0-rc.N` のタグを通し、exe の版の欄・`--version` はタグの名前になる）。リリース候補は GitHub の
  Releases で pre-release になる。
- 公開と非公開の版は同じ番号（開発用の木と公開の木の `Cargo.toml` の `workspace.package.version` を検査でそろえる）。
- CI が検査する: タグの名前が `v` + 版と同じこと（リリース）、main の版が最後のリリースのタグより新しいこと
  （タグのコミットでだけ同じでよい。リリース候補のタグは比べる相手にしない）。`scripts/check_version.py`

## ファイルの形式の版

- ファイルの形式の版は、アプリの版と別に持つ（プロジェクトファイル・システムファイルの `format_version`）。形式が変わったときだけ上げる。
  読み込みの互換は `format_version` で判断する。
- `$schema` の URL（`https://masa-iwm.github.io/lensbench/schema/v0.5/project.schema.json`）とドキュメントの置き場（`/v0.5/`）は
  版の `0.X` まで。`0.5.0-dev`・`0.5.0-rc.1`・`0.5.1` はどれも `v0.5` を指す。lensbench は読むときに `$schema` を無視する。
- 開発中の `v0.X` の置き場には main のスキーマを置き、リリースの後はタグのスキーマに置き換わる（以後は直しの版が同じ置き場を上書き）。
  開発中の版のスキーマはリリースまで動くので、開発版で書いたファイルが最終のスキーマに通らないことはある。
- Y（直し）の版でのスキーマの変更は、互換のある追加だけにする。項目の削除・改名・意味の変更は X を上げる。
- X を上げたら、スキーマ・GUI の見本の組合せ・`examples` の `$schema` を作り直す（`LENSBENCH_UPDATE_SCHEMA=1`・`LENSBENCH_UPDATE_SAMPLES=1`）。

## 変更の記録

- 利用者に見える変更は、その Pull Request の本文の「利用者に見える変更」に 1 行で書き、リリースのときに `CHANGELOG.md` の版の節へまとめる。
- X を上げるリリースには「互換が切れる所」と「結果が変わる所」を書く。互換が切れる変更の細かい移し方は [壊れる変更](changes.md) に。
